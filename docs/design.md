# Design

What the extension owns, what it reads from the host, and the invariants the
tests hold it to. `README.md` states the contract for users; this note says
why the contract holds. `docs/stale-updates.md` proves the rowid guard;
`docs/upstream/` records the host behaviors the design works around;
`docs/review/` holds the measurements behind the numbers quoted here.

## Ownership

An index is three catalog objects in the base table's database, all ordinary
DuckDB objects the extension creates and drops through SQL:

| Object | Name | Holds |
| --- | --- | --- |
| registry row | `__ngram.registry` | `registry_version`, `index_id` (UUIDv4), the owner (schema, table, column, and `owner_key`, a length-prefixed lowercase concatenation of the three names), `format_version`, gram options, `hwm_rowid`, the guard's name and random token |
| segments table | `__ngram.segments_<id>` | one row per (`gram_key`, `segment_no`, `generation`): `postings` BLOB, `rowid_count`, `min_rowid`, `max_rowid`, sorted by key within each generation |
| rowid guard | `__ngram_guard_<hex>` on the base table, named by the index that created it and shared by every index of the table | no postings; the physical dependency that turns covered updates into delete plus append, keeps the moving vacuum off, and records the checkpoint seal and the reuse latch |

A `gram_key` is a fixed-width UHUGEINT of the normalized gram's codepoints
(`ngram_gram_key`), so keys sort and compare without decoding text. A
`segment_no` is `rowid >> 20`: a segment is 2^20 rowids. The row's
`postings` blob is the codec's delta run (`ngram_encode_postings`); the pack
aggregate that produces it holds each posting as a 32-bit offset from the
segment's first rowid while it collects a group.
`generation` 0 is the build; each refresh appends generation `max + 1` for
the rows past the mark; compaction merges the rows of one key and leaves
every survivor at generation 0, so a single-generation table proves itself
merged through its column statistics.

The identity anchor is the guard's token in the registry row. A table has one
guard, shared by every index on it; while the guard exists the host refuses
the renames and dependent drops that could detach the index from the table
it was built from. Every path that reads postings first validates the guard
(the facts the README's staleness section lists), and an index whose guard
cannot be proven falls to `SCAN_ONLY`: exact answers by scanning, maintenance
refused until rebuild. The listing (`ngram_indexes()`) observes registry rows
and stray storage objects together, so an older format or an object without
a row is reported rather than trusted. A database copied and attached under
another name carries a valid index of its own: the catalog name and the
reference together are the identity, which is why the drop by reference takes
a catalog.

## Snapshot and visibility

Postings cover committed rowids at or below `hwm_rowid`. A query answers in
three disjoint parts under the caller's own transaction:

1. **Candidates** from the postings of the needle's rarest grams, intersected
   per segment, then fetched and rechecked against the original predicate.
2. **The tail**: committed rows past the mark, read by a scan positioned at
   the first row group past the mark and bounded by the table's allocated
   rows.
3. **Local rows**: rows this transaction appended, which carry provisional
   rowids past `MAX_ROW_ID` and are read from local storage as their own
   unit of work.

Rechecking makes the candidate set safe to overestimate; the tail makes the
mark safe to lag; the local phase makes an open transaction see its own
writes. Maintenance runs in one transaction per call, generated by the
pragma preprocessor as a script whose first statement acquires the vacuum
fence; a refresh's script ends with its progress row. A refresh's new mark is
the highest committed rowid its packing pass saw, or its bound when rows lie
past the bound, so a rowid that a concurrent append commits later is never
buried under the mark; `ngram_index_stats` counts `remaining_tail` in the
calling statement's snapshot with the same `rowid < MAX_ROW_ID` bound, so
neither ever counts a provisional row.

A refresh with no allocated rowid past the mark and a merge of a
single-generation table are decided at expansion (`DataTable::GetTotalRows`
and the generation column's statistics) and emit only the fence call, plus
the refresh's progress row. The fence's execution-time check repeats the
registry row's mark and gram options and the guard verdict before a byte is
written, so a concurrent refresh, which moves the mark, makes a stale merge
refuse; a row committed after a no-op refresh's expansion stays in the tail
until the next refresh. Refresh and merge append their packed rows through
the fence's append call, a plain transaction-local append, because the
host's batch insert empties a table when an empty batch insert precedes a
large one in the same transaction
(`docs/upstream/duckdb-empty-batch-insert.md`); the
build and the purge, which never follow such a statement, use the batch
insert for its sorted runs.

## The probe and its budgets

A needle is decomposed into distinct gram keys (the transparent path does so
at planning and again at execution); needles longer than sixteen bytes per
admissible key are declined before any gram is extracted.
The manifest scan reads the segments rows of every key of the needle (a
positioned scan per key over the sorted runs, pruned by zone maps) and keeps
the rarest `ngram_max_grams_per_query` keys by posting total. Admission is
decided before any postings blob is opened, from the manifest alone:

- **Work**: the postings the chosen keys would decode, capped by
  `ngram_max_probe_rowids` (`decoded-rowid work budget exceeded`).
- **Memory**: a manifest and one segment workspace per worker are reserved
  against the query's budget (the README's "Querying" section gives its
  size); a needle whose keys alone exceed it, a manifest that does, or one
  posting segment that does is declined (`query grams exceed query memory
  budget`, `segment manifest exceeds query memory budget`, `one posting
  segment exceeds query memory budget`).
- **Density**: the candidate bound per segment is the smallest posting count
  among the keys, discounted for spans dense enough to read as ranges and
  charged for every extra projected column; when the fetch-equivalent sum
  exceeds `ngram_max_candidate_fraction` of the indexed rows, the query scans
  (`docs/review/2026-09-09/README.md` records the measurement behind the
  default of 0.02).

Declined queries take the native scan with the same predicate, so the modes
reported by `EXPLAIN ANALYZE` (`index`, `full scan fallback: <reason>`) are
the only two outcomes and both are exact.

## Publication order and parallelism

Workers claim segments in ordinal order, decode them independently, and hand
each decoded vector to a queue that publishes in ordinal order: a segment
decoded early waits, pending, until every lower ordinal is published, and a
worker with nothing to fetch either decodes the next segment or yields. Each
fetch batch therefore carries a batch index that increases with the rowids
it covers, which is what ordered sinks (`CREATE TABLE AS`, `LIMIT`, streamed
results) rely on to reassemble a parallel scan in rowid order. At most
`max_threads` segments are decoding, pending or published at once, and a
worker fetching a batch holds at most one more vector, which bounds the
published candidate bytes the plan reserves. The harness forces the order
through `src/include/ngram/test_hooks.hpp` (`query/publication-barrier`) and
proves it with an in-order stream.

A batch of at least 256 candidates whose rowids fill at least a quarter of
their span is read by one bounded scan with the predicate pushed down as a
table filter; smaller or sparser batches fetch row by row. Both read the
recheck columns first and fetch the remaining projected columns only for the
rows that passed, so a wide table costs the probe what its kept rows cost.

## Memory and work accounting

Build, refresh and compaction pack postings through one aggregate over
(`gram_key`, `segment_no`) groups whose state stores 32-bit offsets. The
build's and the refresh's packing passes are split into rowid-range
partitions sized from `memory_limit` (`ngram_build_partitions` overrides the
count) so that the aggregate's hash table fits; compaction packs at the
finest partition count. The packed rows are copied once into the segments
table in key order so that each generation is one sorted run. On
the enwik9 corpus (10.9M rows, 0.92 GiB of text) a case-insensitive build
peaks at 6.9 GiB of process memory at 24 threads
(`docs/review/2026-09-09/build_observations.json`), and the release block in
the README reports the case-sensitive index it measures; an index is about
the size of its text.

A query's memory is reserved up front and released with the query, including
on interrupt: the manifest, the per-worker segment workspace, and the
published candidate vectors are charged to one reservation the profiler
reports as the probe's peak (`query/probe-memory-peak` in the harness).

## Host dependencies

- DuckDB v1.5.5 at source `d8cdaa33`, pinned by the `duckdb` gitlink and by
  the guard, which refuses to trust any other host (`docs/UPDATING.md`).
- The custom index type: v1.5.5 lets the guard persist a checkpoint seal and
  refuses guard-touching `ALTER`; a stock host without the extension can read
  a guarded table but not write it.
- The pragma preprocessor, which expands a maintenance pragma into a
  multi-statement transaction; the fence handle ties every generated
  statement to the expansion that produced it.
- Positioned scans through `RowGroup::GetRawColumnData` and
  `ColumnData::CheckZonemap`, and `DataTable::InitializeLocalAppend` for the
  maintenance append. Each is named in `docs/UPDATING.md` as a seam to check
  on a host bump.
- The empty-batch-insert hazard above, and the statistics behavior that keeps
  a deleted generation's column statistics until a checkpoint vacuum or a
  purge rewrites its row groups (why a no-op compaction right after a merge
  in the same session takes the full check).

## What the tests hold

`test/README.md` maps each mechanism to its test. In one line each: every
query shape equals the extension-disabled answer as a multiset in both
directions; every candidate set is a superset of the true matches among
indexed rows; ordered sinks see rowid order at every thread count; an
interrupt at any decode or append point leaves no partial state and no
stranded worker; a kill at any point of a maintenance script leaves a state
the uninterrupted script passes through; and a guard that cannot be proven
is never trusted.
