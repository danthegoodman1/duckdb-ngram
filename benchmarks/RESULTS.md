# ngram benchmark results

Everything here was produced by the scripts in this directory on one machine,
from seeded corpora. Re-running the scripts at a smaller `--replicas` count
reproduces the same shape on smaller hardware.

## Machine

| | |
| --- | --- |
| CPU | 24 cores |
| RAM | 125 GB |
| Disk | NVMe SSD, ~1.7 TB free |
| OS | Linux 7.0.0-27-generic |
| DuckDB | v1.5.5 (`d8cdaa33`), release build with the extension linked in |
| Settings | `threads=24`, `memory_limit='48GB'` unless stated otherwise |

## Corpora

Generated by `gen_corpus.py`; seed `20260809` throughout.

| Name | Source | Rows | Text bytes |
| --- | --- | --- | --- |
| `enwik9` (1 replica) | first 10⁹ bytes of an English Wikipedia XML dump, one line per row | 10,920,423 | 0.919 GiB |
| `code` | every `.cpp`/`.hpp` line of the pinned duckdb checkout | 1,055,570 | 0.051 GiB |

Scale past 1 GB comes from **replication with perturbation**: replica *r* of
source line *i* keeps the line but rewrites three characters, at a position and
with letters derived from `hash(i, r, seed)`. Gram distribution therefore stays
enwik9's — the reason to use real text at all — while no two rows are
byte-identical and no posting list degenerates into N copies of one pattern.
The perturbation is visible in the numbers: it lifts the distinct-gram count
from enwik9's own 605,513 (Phase 2, unperturbed) to 788,596 and the blob ratio
from 0.867 to 0.922, i.e. it makes the index *harder*, not easier. It also adds
~3 MB to a replica (0.919 GiB of source lines become 0.922 GiB of rows) because
lines shorter than 12 characters get the salt appended rather than substituted.

## Reproducing

```sh
NGRAM_REPLICAS=10 bash benchmarks/run_all.sh
```

`run_all.sh` is the exact sequence, in order, that produced everything below.
`NGRAM_REPLICAS` scales the largest corpus: 100 (the default, and what is
recorded here) needs ~200 GB of disk and about seven hours; 10 needs ~20 GB and
about forty minutes and reproduces every shape.

## 1. Where the index's bytes go

`analyze_encoding.py` reconstructs the posting stream with the codec's own
inverse (`ngram_unpack_postings`) and recomputes the encoded size from first
principles. **The model reproduces the real blob total to within 0.0000% on
both corpora**, which is what makes the alternatives below trustworthy: they
are evaluated on exactly the same postings with exactly the same accounting.

### Delta-width histogram

| Bytes per delta | enwik9 1 GB | code |
| --- | --- | --- |
| 1 | 77.07 % | 85.94 % |
| 2 | 21.43 % | 13.17 % |
| 3 | 1.50 % | 0.88 % |
| ≥4 | 0 | 0 |

Mean cost is 1.26 bytes per posting (enwik9) / 1.15 (code). Per-segment headers
— a version byte plus the varint count and first rowid — are **1.6 %** of the
total on enwik9 and 1.1 % on code. There is no per-run overhead worth attacking
and no wide-delta tail worth special-casing.

### Alternative encodings, measured on the same postings

Saving relative to the current LEB128-delta format (positive = smaller):

| Encoding | enwik9 1 GB | code |
| --- | --- | --- |
| Bit-packed FOR blocks, B=32 | +5.8 % | +2.5 % |
| Bit-packed FOR blocks, B=64 | +2.4 % | −4.8 % |
| Bit-packed FOR blocks, B=128 | −1.1 % | −12.5 % |
| Bit-packed FOR blocks, B=256 | −4.6 % | −20.5 % |
| **Per-block best of {bit-packed, varint}, B=32** | **+7.8 %** | **+11.8 %** |
| Per-block best, B=64 | +5.7 % | +9.3 % |
| Per-block best, B=128 | +3.9 % | +7.2 % |
| Roaring-style (bitmap or 16-bit array per 2¹⁶ chunk) | −53.7 % | −62.7 % |

Re-validated at 10 GB, on 7,243,473,657 postings: model 8,566.8 MB of deltas
plus 144.6 MB of headers = 8,711.4 MB against an actual 8,711.4 MB (0.0000 %
error again), delta widths 77.06 / 21.43 / 1.50 %, best hybrid saving 7.8 %.
The conclusion does not move with scale — the distribution at 100× the data is
identical to three significant figures.

**Decision: no encoding change.** The bar set for Phase 6 was a ≥20 % on-disk
win at no correctness risk. The best candidate reaches 7.8 % on natural
language and 11.8 % on code — and that best candidate is also the most complex
one (a per-block format flag, two decode paths, a new format version, and full
differential/churn/crash re-validation). Roaring-style is decisively worse:
these posting lists are far too sparse per 2¹⁶ chunk for bitmaps, and a 2-byte
array entry is worse than a 1.26-byte varint. `format_version` stays at 2.

### Segment granularity

`SEGMENT_SHIFT` buckets postings by `rowid >> SHIFT` (currently 20). Total
encoded bytes as the bucket size changes, enwik9 1 GB:

| SEGMENT_SHIFT | Segment rows | Bytes vs current |
| --- | --- | --- |
| 16 | 13,516,228 | +3.88 % |
| 18 | 5,762,205 | +1.09 % |
| **20 (current)** | **2,549,366** | **0.00 %** |
| 22 | 1,276,770 | −0.43 % |
| 24 | 788,596 | −0.59 % |
| 26 | 788,596 | −0.59 % |

Coarser buckets save at most 0.6 % of bytes while giving the probe's
live-segment and min/max pruning less to work with, and finer buckets cost
real space. **Decision: `SEGMENT_SHIFT` stays at 20.**

## 2. Scale

### Why the corpus is built incrementally

A monolithic build sorts every (gram, rowid) pair at once. Measured here, that
cost is strongly superlinear in the chunk size, because past a certain point
the external sort needs several merge passes:

| Chunk indexed in one statement | Wall | Peak RSS | Spill | Per replica |
| --- | --- | --- | --- | --- |
| 1 replica (0.92 GiB text) | 208 s | 48.3 GB | 24.3 GB | 208 s |
| 5 replicas (4.61 GiB text) | 3058 s | 54.1 GB | 278.4 GB | 612 s |

Five times the data costs fifteen times the time and eleven times the scratch.
Extrapolating the 5-replica point to 100 GB gives ~3.4 TB of spill — more than
the machine has — while the 1-replica point gives 24 GB of spill per step at a
flat 208 s. The 100 GB corpus below is therefore built in 100 single-replica
steps: one `create_ngram_index` and 99 `ngram_refresh` calls.

That is not a benchmark artifact; it is the advice in the README, and it is
also a real-workload exercise of Phase 5's refresh path.

### Build and refresh cost

| Corpus | Step | Wall | Peak RSS | Spill |
| --- | --- | --- | --- | --- |
| 1 GB | `create_ngram_index`, 1 replica | 208.2 s | 48.3 GB | 24.3 GB |
| 10 GB | `create_ngram_index`, 5 replicas | 3058.4 s | 54.1 GB | 278.4 GB |
| 10 GB | `ngram_refresh`, 5-replica tail | 3062.4 s | 57.8 GB | 282.7 GB |
| 10 GB | `ngram_compact` | 15.8 s | 20.0 GB | 0 |
| 100 GB | `create_ngram_index`, 1 replica | 208.0 s | 48.1 GB | 24.9 GB |
| 100 GB | 99 × `ngram_refresh`, 1-replica tail | median **210.3 s** (min 206.7, max 267.7) | median 51.2 GB | median 26.5 GB |
| 100 GB | 100 steps, total | 21,436 s = **5.95 h** | 52.4 GB peak | 27.4 GB peak |
| 100 GB | `ngram_compact` | 9433.5 s = 2 h 37 m | 53.3 GB | 311.6 GB |

**Refresh cost tracks the tail, not the table** — and it does so over two
orders of magnitude of index size. The first five refreshes into a nearly
empty index took 208.0, 208.4, 209.2, 210.1, 208.6 s; the last five, folding
the same 0.92 GiB into an index already covering 91 GiB, took 211.1, 208.7,
208.3, 207.6, 210.8 s. No drift, and spill stayed between 24.6 and 27.4 GB
throughout. The 10 GB pair says the same thing at a coarser grain: folding 5
replicas into an index that already covered 5 cost 3062 s, within 0.2 % of the
3058 s the same 5 replicas cost as an initial build on an empty table. Loading
the rows themselves is negligible either way (0.7–1.3 s per replica).

**Compaction has almost nothing to do on an append-only workload.** Each
refresh generation lands in a fresh rowid range, so generations barely share
`(gram, segment_no)` keys. At 10 GB, 77,275 of 24,992,211 segment rows were
fragmented and merging them took 15.8 s. At 100 GB, compaction ran for 2 h 37 m
with 311.6 GB of spill and merged 258,732,511 segment rows down to 248,445,026
— **4 % fewer rows for 44 % of the time the whole index took to build**, and
the encoded payload shrank by 41.9 MB out of 85.3 GiB (0.05 %). It did rebuild
the stats table from 78,832,107 delta rows (one per gram per generation) to
4,509,928 (one per gram), which is what makes the rarest-first probe read less.
Postings were byte-for-byte identical before and after (72,434,741,725 either
way).

The practical reading, which the README repeats: **compaction is for
delete-heavy or interleaved workloads, not routine post-ingest hygiene.** After
a pure append-and-refresh sequence it costs hours to reclaim single-digit
percentages. The one thing worth having from it — a stats table with one row
per gram instead of one per gram per generation — is a small part of the work
it does.

The compacted database file is *larger* than the pre-compaction one
(181.97 GiB vs 172.54 GiB) because the rewrite leaves the superseded blocks
free inside the file rather than returning them to the filesystem. Plan for
that headroom before running it.

`purge := true` widens the rewrite from fragmented keys to every key, so that
postings pointing at deleted rows are dropped everywhere rather than only where
a merge was rewriting the blob anyway. At 10 GB that is **3599.6 s** (60 min,
52.5 GB peak RSS, 310.9 GB spill) against 15.8 s for the plain variant — 228×
the cost, on a corpus with no deletes to purge. Reach for it after a large
`DELETE`, not otherwise.

### Index size

| Corpus | Text | Rows | Postings | Blob bytes | Blob ratio | DB with index | Base table | Index on disk | On-disk ratio |
| --- | --- | --- | --- | --- | --- | --- | --- | --- | --- |
| enwik9 ×1 | 0.922 GiB | 10,920,423 | 724,346,305 | 0.850 GiB | 0.922 | 1.712 GiB | 0.681 GiB | 1.031 GiB | **1.118** |

| code | 0.051 GiB | 1,055,570 | 33,229,791 | 0.036 GiB | 0.708 | 0.082 GiB | 0.031 GiB | 0.050 GiB | 0.995 |

"Base table" is the blocks the corpus column occupies
(`pragma_storage_info`), and "index on disk" is the rest of the database file.
Cross-check at 1 replica: the same corpus loaded into a database with no index
at all is 745,549,824 bytes = 0.694 GiB, 13 MiB above the block count, which is
the file header and catalog. DuckDB's own storage overhead on top of the
encoded blobs is 1.21× — the varint payload is high-entropy and does not
lightweight-compress. (`pragma_storage_info` on the segments table reports far
fewer blocks than the blobs occupy — 0.286 GiB at 1 replica — because large
blobs live in overflow blocks it does not attribute; the file-difference
figures above are the real ones.)

Postings per byte of text is constant across scales (0.768), and so is the blob
ratio (0.922–0.925), which is what makes the extrapolation below
straightforward. The 10 GB on-disk ratio is the outlier at 1.060 rather than
~1.12; it was built in 5-replica chunks, which pack more postings into each
segment row and so pay DuckDB's per-row overhead fewer times.

The size figures above are the state after building. Running `ngram_compact`
grows the file (172.54 GiB → 181.97 GiB at 100 GB) without changing the
payload, since the superseded blocks stay free inside the file.

### Latency measurement protocol

`bench_latency.py`, extending the Phase 3 protocol:

* one warmup, then repeated timed runs **inside one process**, so process
  start-up is never counted; timings come from the engine's own `.timer`
  rather than from wall clock around a subprocess;
* p50 and p95 over the samples (11 repeats at 1 GB, 9 at 10 GB, 5 at 100 GB —
  a single dense-needle scan at 100 GB is tens of seconds);
* **count-equality assertion on every pair** (row-level set identity is covered
  by the differential harnesses and `ngram_parallel.test`). A faster
  wrong-count answer fails the run;
* cold-cache runs evict the page cache (`sync` + `drop_caches`) before each
  sample.

Three pairs per needle:

| Pair | Index side | Comparison side |
| --- | --- | --- |
| transparent | `WHERE s LIKE '%needle%'` with `ngram_auto_accelerate=true` | the identical query under `disabled_optimizers='extension'` |
| explicit | `ngram_search(...)` | `contains(lower(s), needle)` |
| probe | `ngram_candidates(...)` | — (isolates probe cost from fetch+recheck) |

The transparent pair is the headline: same SQL, same semantics, same rows, one
setting apart. The selectivity gate is disabled (`ngram_max_candidate_fraction
= 1.0`) for these runs so that the index path is actually measured rather than
falling back — measuring where it *should* fall back is the point of the
crossover sweep below.

Needles are chosen once, at 1 GB, by measured selectivity from a fixed
candidate list, then reused at every scale — under replication the share of
rows a needle matches is scale-invariant, so a row of the scaling table
compares like with like:

| Class | Needle | Rows matched at 1 GB | Share |
| --- | --- | --- | --- |
| rare | `supercalifragilistic` | 7 | 6.4 × 10⁻⁷ |
| moderate | `Wikipedia:` | 22,380 | 2.0 × 10⁻³ |
| dense | `and t` | 387,629 | 3.6 × 10⁻² |

### What the shape says

**The probe, not the fetch, is the cost for a selective needle.** At 100 GB,
0.564 s of the rare needle's 0.641 s is the probe, and the probe is
single-threaded (user/real ≈ 1.0 in every rare measurement, against ≈ 23 for
the parallel scan it is racing). Its cost is Σ(posting-list length) over the
grams it examines, and those lists grow with the corpus however selective the
needle is: `supercalifragilistic` matches 88 rows out of 1.09 billion and still
decodes three corpus-scale posting lists.

This is why `ngram_max_grams_per_query` turned out to matter more than anything
else measured here. The same tables at the old default of 8 read 0.033 / 0.110
/ 1.762 s for the rare needle and 0.045 / 0.366 / 5.279 s for the moderate one
— the K change alone is worth **2.7× at 100 GB on the rare needle and 3.0× on
the moderate one**, and it is what turns the rare-needle curve from "peaks at
10 GB and falls back" into one that holds its ratio as the corpus grows
(1.6× → 6.5× → 6.7×).

**The design target: met warm, missed cold.** The plan asks for "hundreds of
milliseconds p95 for a selective needle". At 100 GB that is 0.643 s warm — met,
at the top of the range — and 3.217 s cold, which is not. At 10 GB both hold
comfortably (0.073 s warm, 0.157 s cold). The cold gap is disk, not CPU: the
100 GB database is 182 GB against 125 GB of RAM, so a cold probe reads posting
lists from NVMe. Recorded honestly in the gate row rather than rounded into a
pass.

## 3. Tuning sweeps

Two defaults changed on this evidence; two were confirmed. In every sweep the
**answer never changed** — match counts were identical at every setting, which
is the superset invariant doing its job: probing fewer grams can only widen the
candidate set, and the gate only ever chooses between two exhaustive
strategies.

### `ngram_max_grams_per_query`: 8 → 3

Total `ngram_search` time (p50 s) against the number of rarest grams probed:

| K | 10 GB rare | 10 GB moderate | 10 GB dense | 100 GB rare | 100 GB moderate | 100 GB dense | bigram-index rare |
| --- | --- | --- | --- | --- | --- | --- | --- |
| 1 | 0.062 | 0.123 | **2.522** | 0.545 | 2.151 | **30.704** | 0.144 |
| 2 | **0.061** | **0.122** | 2.679 | **0.465** | **2.001** | 33.354 | 0.053 |
| 3 | 0.066 | 0.138 | 3.262 | 0.640 | 2.315 | 39.614 | 0.052 |
| 4 | 0.074 | 0.152 | 3.271 | 0.799 | 2.656 | 38.969 | **0.050** |
| 6 | 0.089 | 0.199 | 3.266 | 1.214 | 3.484 | 39.332 | 0.067 |
| 8 (old default) | 0.110 | 0.362 | 3.235 | 1.750 | 5.980 | 38.742 | 0.096 |
| 12 | 0.185 | 0.364 | 3.216 | 2.999 | 5.965 | 38.807 | 0.177 |
| 16 | 0.341 | 0.362 | 3.208 | 5.211 | 6.001 | 38.509 | 0.306 |

A shallow floor at 2–4 and a steep right arm. K=8 costs 2–4× the floor; K=16
costs up to 11×. The reason is visible in the candidate counts: at 100 GB the
rare needle's candidate set is 2,522 at K=2 and 951 at K=8 — the extra six
posting-list decodes buy 1,571 fewer candidates, which at ~300 ns each is worth
half a millisecond, against 1.27 s of extra probe.

**Three, not two.** K=2 is the fastest setting on natural language, but the
last column is why the default is 3: on an index whose grams are deliberately
dense (the gram-size-2 build of the same corpus), K=2 leaves 97,127 candidates
— 0.89 % of rows — against K=3's 31,008 (0.28 %). At 0.89 % a corpus slightly
denser than this one trips `ngram_max_candidate_fraction` and gives up the
index entirely, paying the probe and then scanning anyway. Three keeps a real
three-way intersection and sits at the floor everywhere measured.

### `ngram_max_candidate_fraction`: 0.05 → 0.01

The gate runs *after* the probe, so it cannot recover probe cost. Its only job
is choosing between fetching the candidates and scanning the table for the work
that remains, which makes the right threshold the point where fetch cost equals
scan cost:

| Corpus | fetch cost per candidate | full parallel scan | break-even candidates | break-even fraction |
| --- | --- | --- | --- | --- |
| 1 GB | 228 ns | 0.046 s | ~175,000 | 1.6 % |
| 10 GB | 252 ns | 0.427 s | ~1,400,000 | 1.3 % |
| 100 GB | 279 ns | 4.623 s | ~11,700,000 | 1.1 % |

Remarkably stable, and 0.05 sits four to five times above it. The candidate
ladder confirms the choice end to end at 100 GB — index path against plain
scan, gate disabled, over 21 needles spanning six orders of magnitude of
selectivity:

| --- | --- | --- | --- | --- |
| `supercalifragilistic` | 8.7 × 10⁻⁷ | 1.792 | 4.452 | **0.40** |
| `the quick brown fox` | 1.2 × 10⁻⁶ | 2.342 | 4.657 | **0.50** |
| `photosynthesis` | 3.8 × 10⁻⁵ | 2.164 | 3.843 | **0.56** |
| `Schwarzschild` | 1.0 × 10⁻⁵ | 2.552 | 3.174 | **0.80** |
| `bicameral legislature` | 7.2 × 10⁻⁶ | 3.328 | 3.532 | **0.94** |
| `philosophy` | 1.0 × 10⁻³ | 4.008 | 3.910 | 1.02 |
| `astronomical` | 2.1 × 10⁻⁴ | 6.136 | 4.709 | 1.30 |
| `Ethelred` | 1.5 × 10⁻⁵ | 9.738 | 3.028 | 3.22 |
| `government` | 5.0 × 10⁻³ | 17.835 | 3.765 | 4.74 |

(Full 21-row ladder in `e100.sweep.json`; the 10 GB ladder has the same shape.)

The ladder is **not monotonic in selectivity**, and that is the most useful
thing in it. `Ethelred` matches 1.5 × 10⁻⁵ of rows yet costs 3.2× a scan, while
`philosophy` matches 70× more rows and roughly ties. The difference is the
grams, not the answer: `Ethelred` is eight characters, so all six of its grams
are probed — including `the`, whose posting list is 196 million entries.
`photosynthesis` has twelve grams, so rarest-first can drop the dense ones.
**Cost tracks the densest gram probed, not the rarity of the needle.** No
candidate-fraction threshold can see this, because it is all spent before the
gate is reached; lowering K is the only control over it.

Checked against the ladder, 0.01 fires correctly on every point: it leaves the
index alone at `Wikipedia:` (2.1 × 10⁻³, index 5.36 s vs a 7.42 s fallback) and
at `government` (5.0 × 10⁻³, index 17.8 s vs an estimated 20.0 s fallback), and
it fires at `American`, `which`, `ing the`, `and t`, `ion` and `the`, where the
fallback is cheaper.

### What the gate costs when it fires

The in-scan fallback does not re-plan; it degrades to a parallel full scan with
the filters applied natively, plus one pass of the recheck expression over the
survivors. It is not free, because the probe is already paid for:

| Corpus | class | gated fallback | plain seq scan | ratio |
| --- | --- | --- | --- | --- |
| 10 GB | rare | 0.503 | 0.393 | 1.28 |
| 10 GB | moderate | 0.563 | 0.252 | 2.23 |
| 10 GB | dense | 1.819 | 0.423 | 4.30 |
| 100 GB | rare | 6.591 | 4.495 | 1.47 |
| 100 GB | moderate | 7.424 | 3.092 | 2.40 |
| 100 GB | dense | 20.101 | 4.745 | 4.24 |

Almost all of the excess is the wasted probe (15.2 s of the dense 100 GB
fallback's 20.1 s). This is the strongest argument for leaving
`ngram_auto_accelerate` off unless you know your needles are selective: an
unlucky needle costs you the probe whether or not the index ends up helping.

| --- | --- | --- | --- | --- | --- | --- | --- | --- | --- |
| 2 | 205.3 s | 533,556,095 | 0.534 GiB | **0.579** | 165,230 | 1.249 GiB | 5,823 | 0.079 | 0.086 |
| **3** | 208.2 s | 724,346,305 | 0.850 GiB | 0.922 | 788,596 | 1.712 GiB | **8** | **0.033** | **0.033** |
| 4 | 222.8 s | 799,490,612 | 1.165 GiB | 1.263 | 4,795,643 | 2.506 GiB | 9 | 0.195 | 0.186 |

Gram 2 is by far the smallest index — 37 % less than gram 3 — but it destroys
selectivity: the same rare needle yields 5,823 candidates instead of 8, 728×
more, and the query is 2.6× slower. Gram 4 barely improves on gram 3's
selectivity (9 candidates vs 8) while costing 37 % more space and 5.6× the
probe time, because its dictionary is 4.8 million grams and the probe reads the
stats table. **Gram 3 is the right default**; gram 2 is the setting for a
space-constrained index whose needles are long, and gram 4 is not recommended
on this evidence.

Covered in section 1 (encoding, segment granularity) and section 2
(`preserve_insertion_order`). All three were measured and left alone.

## 4. Parallel fetch and recheck

Phase 3 measured the dense-needle case losing 3.9× to a 16-thread scan, with
single-threaded fetch as the only cause. Both query paths now run fetch,
recheck and the tail/fallback scan on as many threads as there is work for.

**Method.** The pre-parallel code ran the whole pipeline on one thread whatever
the thread setting was, so `threads=1` reproduces it exactly; the comparison is
against the same 24-thread scan both versions were racing. Everything else —
binary, corpus, needles, gate disabled — is identical. Both sides of this table
were measured at `ngram_max_grams_per_query = 8`, the default at the time, so
the comparison is internally consistent; the K change is a separate, additive
win measured in section 3.

| Corpus | class | index, 1 thread (before) | index, 24 threads (after) | speedup | 24-thread scan | before vs scan | after vs scan |
| --- | --- | --- | --- | --- | --- | --- | --- |
| 10 GB | rare | 0.119 | 0.110 | 1.08× | 0.383 | 0.31× | 0.29× |
| 10 GB | moderate | 0.561 | 0.366 | 1.53× | 0.251 | 2.24× slower | 1.46× slower |
| 10 GB | dense | 10.016 | 3.138 | **3.19×** | 0.427 | 23.5× slower | 7.35× slower |
| 100 GB | rare | 1.904 | 1.762 | 1.08× | 4.213 | 0.45× | 0.42× |
| 100 GB | moderate | 23.082 | 5.279 | **4.37×** | 2.886 | 8.00× slower | 1.83× slower |
| 100 GB | dense | 218.887 | 34.367 | **6.37×** | 4.623 | 47.4× slower | 7.43× slower |

The worst case at 100 GB went from 3 minutes 39 seconds to 34 seconds. The
speedup grows with the amount of fetching to be done — 1.08× where there is
none (the rare needle is all probe), 6.37× where there are 68 million rows to
fetch and recheck — which is exactly the shape a correct parallelization should
have.

**What it moved, in the terms that matter.** Fetch cost fell from ~2,970 ns to
~279 ns per candidate at 100 GB, which moves the fetch-vs-scan break-even from
0.14 % of rows to 1.1 % — **the band of selectivities where using the index
beats scanning is now about eight times wider.** That is the concrete payoff,
and it is what let `ngram_max_candidate_fraction` be re-anchored upward from
its true pre-parallel crossover rather than downward.

**What it did not fix.** The packet's crossover analysis predicted parallelism
would put the worst case near 0.2 s. It does not: the dense case is 3.1 s at
10 GB and 34 s at 100 GB, because fetching and rechecking tens of millions of
individual rows is expensive however many threads do it, and because the probe
(1.4 s and 15.2 s respectively) is still single-threaded and is not fetch work
at all. Parallel fetch removes a 6× penalty; it does not make dense needles a
good idea. That is the gate's job, and the gate is why the default path never
pays these numbers.

**The fallback benefits too.** Before this change, a gated scan degraded to a
*single-threaded* full scan — strictly worse than the sequential scan it had
replaced. It is now a parallel scan; the measured cost of a fired gate (section
3) is 1.3–4.3× a plain scan, and essentially all of that excess is the wasted
probe rather than the scan itself.

## 5. Extrapolation to a terabyte

A true TB corpus does not fit on this machine: 1 TB of text plus a ~1.06 TB
index plus scratch exceeds the 1.7 TB available, and a monolithic build of that
size is impossible regardless (section 2). What follows is extrapolation from
the measured 1 → 10 → 100 GB curve, with its assumptions stated so the reader
can discount it.

| Quantity | Basis | 1 TB projection |
| --- | --- | --- |
| Index build | 208–211 s per 0.92 GiB replica, flat across 100 chunks spanning a 100× range of index size | ~1,085 chunks ≈ **63 h**, ~27 GB scratch at any moment |
| Index size | blob ratio 0.922 constant at 1/10/100 GB; on-disk ratio 1.06–1.12 | ~0.92 TiB of blobs, ~1.06–1.12 TB on disk |
| Refresh | cost tracks tail size only, measured invariant over 100 refreshes | ~210 s per GiB appended, independent of table size |
| Compaction | 2 h 37 m at 100 GB, dominated by rewriting every posting | ~26 h, and worth even less than at 100 GB |
| Rare-needle query | probe is Σ(posting-list length) over the probed grams, linear in corpus: 0.026 → 0.059 → 0.641 s at the shipped K=3 | **~6.4 s warm, ~32 s cold** — an order of magnitude past the target |
| Full parallel scan | 0.046 → 0.427 → 4.623 s, linear | ~46 s |

The one headline worth carrying: **the index still beats a scan at 1 TB —
roughly 6.4 s against 46 s for a rare needle, ~7× — and that ratio is stable
across every scale measured (6.5× at 10 GB, 6.7× at 100 GB). What does not hold
is absolute latency.** The "hundreds of milliseconds" target is met warm at
100 GB (0.643 s p95) and lost somewhere between there and a terabyte.

Assumptions, and which way each biases the result:

1. **Gram distribution is scale-invariant.** Guaranteed by construction here —
   every replica draws from enwik9 — and *conservative* for probe cost: a real
   1 TB corpus of diverse text would have a larger gram dictionary and
   therefore shorter lists per gram, making the probe cheaper than projected.
   The dictionary does still grow in this corpus (788,596 grams at 1 replica,
   4,509,928 at 100) because the perturbation salt adds grams.
2. **Linear probe cost.** Measured 1 → 10 GB is 3.3× for 10× data and
   10 → 100 GB is 16× for 10× data, i.e. slightly *worse* than linear at the
   top end. The projection uses linear, so it is optimistic there.
3. **I/O is not the wall.** At 100 GB the database (182 GB) already exceeds
   RAM (125 GB), and cold is 5× warm for the rare needle (3.217 s against
   0.641 s). At 1 TB essentially everything is cold, so the cold column is what
   a user would actually see: ~32 s extrapolated, against ~46 s for a cold
   scan. The margin narrows to almost nothing.
4. **Nothing in the storage layer degrades non-linearly.** The segments table
   would hold ~2.6 billion rows at 1 TB. Zone-map pruning of the per-gram
   equality filter is what keeps that scan affordable, and it has been measured
   only up to 258 million rows. This is the largest unquantified risk.

**True-TB validation requires hardware this project does not have.** The gate
was revised accordingly (see the plan); whether to provision it is the user's
call.
